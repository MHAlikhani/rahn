# Stage 7 Report — v0.7.0-alpha: Execution Backends

Date: 2026-08-06. ADR: [0016](../../adr/0016-execution-backends.md). Release: **v0.7.0-alpha**.

## Objective

Separate abstract network state from backend execution via a clean backend abstraction (charter Stage 7), keeping simulation-first and fail-safe principles, without implementing new dataplanes.

## Research motivation and architecture decision

The Stage 3 backend was hard-wired into the CLI (`rahn-exec` free functions), making simulation a special case and every future backend (eBPF/XDP, P4-class dataplanes) a copy of the gating/safety wiring. ADR 0016 defines:

- **`ExecutionBackend` trait** (`rahn-sim::backend`): `name()`, `capabilities()`, and a *pure* `plan(current, target) -> Vec<BackendStep>`; determinism is a contract, not a hope.
- **Two-level step model:** `Describe(Action)` — model-level, from the dependency-safe plan — or `Invoke { program, args }` — concrete host invocation. A backend returns one kind exclusively. Simulation returns Describe only; a real backend's dry run is its model-level counterpart rendered without execution.
- **Capabilities:** `link_topology / addressing / traffic_control`; requirements a backend cannot realize fail explicitly (never silent partial execution). eBPF/XDP become future trait implementations plus capability entries — no dataplane code exists in this stage.
- **Safety:** simulation remains the default backend and cannot execute by definition (structured refusal even with the gate flags); real execution still requires `--execute --yes-i-know`; ADR 0012 host-safety rules (host-side argv limited to `rahn-*` namespaces) are unchanged and structurally asserted.

## Implementation changes

- `rahn-sim::backend` — trait, `BackendStep`, `Capabilities`, `SimulationBackend`.
- `rahn-exec::backend` — `LinuxNamespaceBackend` implementing the trait (delegating to the unchanged ADR 0012 mapping); `execute()` (Linux + root gate) moved into the backend.
- CLI: `rahn apply --backend <name>` (default `simulation`); explicit registry (`simulation`, `linux-ns`) with unknown-name rejection; dry runs render either step kind. No addressing, traffic control, or new networking features.

## Tests

- Backend determinism: simulation and linux-ns plans are pure functions of inputs (unit tests).
- linux-ns step shape: 12-step instantiation sequence identical to ADR 0012; host-safety mapping unchanged.
- CLI e2e: default simulation output; linux-ns dry run showing exact argv; unknown-backend explicit failure; simulation+`--execute` structured refusal; `--execute` without `--yes-i-know` still a usage error.
- Real namespace execution unchanged (Linux CI job, `#[ignore]` test) — call path migrated, semantics identical.
- Workspace: 128 tests green; fmt and clippy (`-D warnings`) clean; release build clean.

## Limitations

- Capability set is coarse (booleans); dataplane backends may need finer-grained negotiation (extension point: the `Capabilities` struct, via ADR).
- Backends are synchronous, whole-plan (no streaming/partial apply); the O(m·n) batch-apply debt still applies upstream of `plan()`.
- Only two backends exist; the abstraction's fitness for genuinely different targets (eBPF) is argued, not yet demonstrated.
- No CLI listing command for backends (registry is documented in `--backend` errors).

## Future work

- eBPF/XDP backend (its own ADR: privilege model, program lifecycle).
- Capability-aware `rahn backends` listing; backend-specific destroy scoping.
- Packing/batched sync transport (Stage 6 debt) before distributing large plans.
