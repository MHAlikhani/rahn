# Stage 6 Report — v0.6.0-alpha: Distributed State

Date: 2026-07-19. ADR: [0015](../../adr/0015-distributed-state.md). Release: **v0.6.0-alpha**.

## Objective

Define and demonstrate a defensible distributed-state model — identity, authority, consistency, replication, partitions, conflicts, recovery, convergence — without "adding clustering" (charter Stage 6; RQ7 requirements-first).

## Research conclusions (RQ7 answers, condensed from ADR 0015)

- **Strongly consistent:** each replica's own committed history only (read-your-writes; hash-verified immutable records).
- **Eventually consistent:** cross-replica visibility, converging only via explicit sync.
- **Authority:** every replica is authoritative for its own history; no leader; **no epoch/generation concept** — without leader election there is nothing an epoch orders (deliberate non-concept).
- **Partition:** local writes remain available; divergence is represented, not prevented (CAP: local availability + local consistency, cross-replica consistency deferred to healing).
- **Conflicting transitions:** divergent tips over a common ancestor; conflicts are the existing semantic merge conflicts — detectable, explainable, fail-closed, never auto-resolved.
- **Recovery:** reopen store; fetch missing objects by hash; corrupted payloads refused by hash verification; partial recovery is normal.
- **Guarantees claimed:** immutability, hash integrity, deterministic convergence (byte-identical merge commits), read-your-writes, monotonic per-replica history. **Not claimed:** linearizability, serializability, cross-replica strong consistency.

## Implementation changes

- New crate **`rahn-dist`**: deterministic two-way sync engine —
  - `offer`: branch-tip advertisement;
  - `fetch_missing`: copy missing commits + states by hash (complete ancestries only; a replica never adopts a tip whose ancestry is incomplete);
  - strict-ahead/behind adoption; true divergence → fail-closed semantic merge over the common ancestor; a successful merge creates a **byte-identical merge commit on both replicas** (parents ordered lexicographically by commit id, message `sync merge`, constitution-checked);
  - `SyncReport` per-branch outcomes: `UpToDate | Fetched | Merged(id) | Conflict(report)`.
- **No new concepts beyond the model:** ReplicaId (self-asserted), Offer, per-branch outcomes. Epoch/ReplicationEvent/SyncState were considered and deliberately *not* added (no concrete purpose in this model — ADR 0015).
- CLI unchanged: sync is a library prototype in v0.6 (a `rahn sync` command is proposed for Stage 7 alongside the backend work); this kept the stage focused on semantics.

## Partition model (tested scenarios, all deterministic, in-memory stores)

Diverge during "partition" (independent local commits) → reconnect (`sync_pair`) → disjoint changes converge with identical merge commits; conflicting changes fail closed with divergent tips **persisting** across repeated syncs; restart recovery reopens the store and completes fetch; corrupted replication data refused loudly; duplicated/reordered/repeated syncs are idempotent.

## Experiments and benchmark results

Environment: Windows 11 (build 28000), i5-12450HX, 12 GB RAM, rustc 1.99.0-nightly, commit `269edb1`+, release build, medians. Harness: `crates/rahn-dist/tests/sync_scaling.rs` (`cargo test -p rahn-dist --release --test sync_scaling -- --ignored --nocapture`).

| commits | offer (ms) | sync (ms) | objects replicated |
|---:|---:|---:|---:|
| 10 | 0.275 | 21.2 | 20 |
| 100 | 0.285 | 144.7 | 200 |
| 1 000 | 0.251 | 2 981.0 | 2 000 |
| 10 000 | 0.120 | 80 850.6 | 20 000 |

Interpretation (scoped, single machine):

- `offer` is O(1)-ish (branch map read).
- **Sync cost is ~3–8 ms per object** — dominated by per-object file open/rename and double SHA-256 hashing on fetch, on Windows NTFS. This is the stage's known performance debt: a packfile/batched-transfer design (single archive per offer, verify-on-arrival) would amortize it substantially and is the natural Stage 7 follow-up (its own ADR).
- Convergence itself is cheap once objects are local; the cost is transport-shaped, not algorithm-shaped.

Behavior under partition is covered by the scenario tests, not timings (there is no network: partitions are simulated by construction).

## Tests

- 7 scenario tests: identical histories UpToDate; strict-ahead/behind adoption in both directions; disjoint divergence → identical merge commits on both replicas; fail-closed conflict with **persistent divergence** (re-sync reproduces the conflict); restart recovery (reopen from disk only); corrupted-object refusal; idempotent duplicated/reversed sync.
- Workspace: 126 tests green; fmt and clippy (`-D warnings`) clean.

## Security review

Replica identity is self-asserted; there is no authentication — the trust boundary is the transport peer list (documented in ADR 0015). Hash verification detects corruption and forged *content*; it does not prevent unauthorized *authorship* (signed transitions remain Future). Replay is harmless: sync is idempotent and content-addressed. No PKI built — deliberately deferred.

## Limitations

- Per-object transport cost (above) — no packing.
- Observations and causal logs are per-replica local; log replication is Future.
- No authentication/authorization; single-branch-per-name sync (no multi-remote config surface); no CLI command yet.
- Merge determinism relies on identical constitution files on both replicas (diverged constitutions are themselves a conflict class not yet detected — documented gap).

## Unresolved questions

- RQ7 follow-up: do real deployments need a single-writer mode (and thus epochs/leader election)? Evidence gathering deferred until execution backends produce multi-site workloads.
- Constitution divergence across replicas: detect and report as a first-class conflict?
