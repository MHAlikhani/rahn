# Stage 3 Report — v0.3.0-alpha: Isolated Linux Execution

Date: 2026-05-26. ADR: [0012](../../adr/0012-linux-ns-execution.md). Release: **v0.3.0-alpha**.

## Objective

First real-network interaction, in isolation: instantiate an abstract RAHN topology inside Linux network namespaces with explicit opt-in, simulation as default, and structural host-safety guarantees (charter Stage 3 gate).

## Implementation changes

- New crate **`rahn-exec`**: pure, deterministic mapping from `rahn-sim` execution plans to ordered `ip` (iproute2) argv vectors. Nodes → network namespaces (`rahn-<node>`); interfaces → `dummy` interfaces; links → veth pairs (deterministic IFNAMSIZ-safe names: `r` + 7 hex chars of SHA-256 of the endpoint); loopback raised per namespace.
- CLI: `rahn apply <ref>` prints the exact argv sequence (simulation, default). `rahn apply <ref> --execute --yes-i-know` executes for real; `rahn destroy --yes-i-know <ref>` deletes the state's namespaces (recovery path for partial failures). `--execute` without `--yes-i-know` is a usage error (test-enforced).
- Platform gate: execution and destroy refuse at runtime on non-Linux (dev machine is Windows; see limitations).

## Architectural changes

- Execution plane is now a real backend behind the plan format (the Stage 2 seam held — no core changes were required to add it, which is itself evidence for RQ8's design question).
- Host-safety invariant is structural and test-enforced: host-side argv is limited to `ip netns add/del rahn-*`; all other commands are namespace-scoped (`ip -n rahn-* …`). `assert_host_safety` encodes this and panics on violation.

## Experiments

- **E6 (partial): plan/observation differential check** — on Linux CI, the real-execution test instantiates a 2-node/1-link topology and verifies observed namespace state (`ip netns list`, `ip -n rahn-a link show`) contains the planned objects, then verifies full teardown. No mismatches observed in the tested scenario. Scoped: 2 nodes, 1 link, no addressing/traffic.
- E2/E3/E4/E5: unchanged status (planned).

Not applicable this stage: no performance claims are made for namespace setup/teardown (the stage report for v0.2 remains the only timing evidence).

## Tests

- `rahn-exec` unit tests (6): deterministic IFNAMSIZ-safe veth naming, pure mapping and command ordering (12-command instantiation sequence pinned), **host-safety invariant** over build and teardown, long-interface-name refusal before any command, non-Linux refusal, destroy coverage.
- `linux_real` integration test (Linux + root, `#[ignore]`): full instantiate → observed-state assertions → destroy → absence assertions. CI runs it on ubuntu with sudo.
- CLI: `--execute`/`--yes-i-know` gating (parse-level and platform-level), dry-run output shape.
- Workspace: 98 tests green; fmt and clippy (`-D warnings`) clean.

## Documentation changes

- ADR 0012; `docs/spec/execution.md` normative for the namespace backend; ROADMAP stage 3 marked; CHANGELOG 0.3.0-alpha; README status (execution exists, opt-in, Linux-only).

## Limitations

- **No addressing yet** (Stage 2 deferral): namespaces have links but no IPs; connectivity is link-existence only — ping validation waits for addressing.
- **Windows dev machine cannot run real execution**; the Linux path is validated exclusively by CI (ubuntu, sudo). First CI run is the real test of the workflow.
- Root requirement: netns creation needs CAP_SYS_ADMIN; no unprivileged mode attempted.
- Failure recovery is whole-state destroy, not per-command rollback.

## Unresolved questions

- RQ8 (multi-backend): one backend exists; the plan-seam worked unchanged — evidence, not proof, of backend neutrality.
- Addressing + `tc` (traffic control) are the natural Stage 3.5 additions; both fit the argv mapping or motivate netlink (new ADR).

## Next-stage implications

- Stage 4 (observability) can consume per-command results; the O(m·n) batch-apply debt becomes relevant for observation ingestion volumes.
